# Panduan Buku Besar (Ledger) Database ReLoop

Berbeda dengan sistem *wallet* tradisional yang sering kali hanya memperbarui kolom `balance` (saldo) secara langsung, ReLoop menggunakan sistem **Ledger (Buku Besar) Append-Only**.

Sistem ini memastikan bahwa setiap perubahan saldo pengguna, organisasi, atau pengepul memiliki rekam jejak (*audit trail*) yang tidak bisa diubah (*immutable*).

## 1. Tabel Utama: `RewardLedger`

Tabel `RewardLedger` mencatat semua arus masuk dan keluar poin/uang dalam platform.

### Kolom Kunci:
- `userId`: Pengguna yang memiliki saldo tersebut.
- `entryType`: Jenis entri ledger (`EARN`, `REDEEM`, dll.).
- `reasonCode`: Alasan bisnis, misalnya:
  - `DEPOSIT_ACCEPTED` / `ITEM_ACCEPTED`: Pendapatan dari setoran mesin RVM.
  - `TRASH_BAG_RETURN`: Reward pengembalian trash bag setelah check-out trip wisata (`referenceType: Trip`, business key `trip:<tripId>:return`, maksimal satu per trip).
  - `TOURISM_COMPLIANCE_BONUS`: Bonus demo/seed kepatuhan wisata (bukan jalur produksi utama).
  - `REDEMPTION_RESERVE` / `REDEMPTION_SUCCESS`: Pencairan ke e-wallet / bank.
- `status`: Status dari transaksi tersebut:
  - `PENDING`: Poin sudah didapat tapi masih ditahan (misal: mesin belum di-verifikasi, atau sedang dalam proses pencairan). Saldo jenis ini belum bisa dibelanjakan.
  - `AVAILABLE`: Poin sudah sah dan bisa ditarik/dibelanjakan oleh pengguna.
  - `REDEEMED`: Saldo sudah berhasil ditarik menjadi uang riil.

## 2. Cara Menghitung Saldo Akhir (Balance)

Karena tidak ada kolom khusus `current_balance` pada entitas User, maka saldo total pengguna dihitung secara agregat *(sum)* dari seluruh baris di `RewardLedger` miliknya.

**Rumus** (`computeBalance` di `lib/ledger.ts`, satu-satunya definisi):
- `Saldo tersedia = SUM(amount)` EARN/ADJUST/REVERSE/PENALTY berstatus `AVAILABLE` + REDEEM berstatus `PENDING` (reserve pencairan) dan `REDEEMED` (sudah dibayar).
- `Menunggu pemeriksaan = SUM(amount)` EARN/ADJUST/REVERSE/PENALTY berstatus `PENDING` (ADJUST `PENDING` tidak menambah saldo tersedia).
- `Sedang dicairkan = -SUM(amount)` REDEEM `PENDING`; `Sudah dibayar = -SUM(amount)` REDEEM `REDEEMED`. REDEEM `REVERSED`/`REJECTED` tidak berpengaruh.

*Catatan: Nilai transaksi keluar (penarikan tunai) dicatat sebagai angka negatif (contoh: `-50000`) dengan status REDEEM `PENDING`/`REDEEMED`, bukan `AVAILABLE`. Karena itu `SUM(amount) WHERE status = 'AVAILABLE'` saja TIDAK mengurangi pencairan dan bukan saldo (kesalahan LOG-07 yang diperbaiki M05).*

## 3. Keuntungan Sistem Append-Only

1. **Anti-Fraud**: Tidak mungkin ada admin nakal yang bisa "mengubah" saldo `100` menjadi `1000` dengan mengubah satu angka. Mereka harus membuat transaksi buatan baru (yang akan terdeteksi di log).
2. **Rekonsiliasi Keuangan**: Sistem ini sangat disukai oleh akuntan mitra karena setiap perak yang keluar bisa ditelusuri riwayat asalnya.
3. **Mutasi saldo diserialkan per pengguna**: Menulis baris baru saja tidak mencegah dua pencairan paralel memakai saldo yang sama (keduanya bisa membaca saldo lama). Karena itu setiap mutasi saldo mengikuti aturan di bawah.

## 4. Aturan transaksi saldo (M01)

- Saldo tetap dihitung dari ledger (`getWalletBalance(userId, tx?)`); tidak ada kolom saldo kedua.
- Setiap transaksi yang menulis EARN/ADJUST/REVERSE/PENALTY/REDEEM memanggil `lockUser(tx, userId)` (`lib/db-locks.ts`, `SELECT ... FOR NO KEY UPDATE`) lebih dulu, lalu membaca saldo, status, kepemilikan, dan idempotency melalui `tx` yang sama. Isolasi transaksi ReadCommitted eksplisit. Pengajuan pencairan, reward trip (M03), serta penerimaan mesin, penahanan fraud, dan peninjauan setoran (M04) mengikuti aturan ini; rollout uang tetap tertahan di gate Z01.
- Urutan lock global: User -> PayoutAccount -> RewardFundingAccount -> Campaign -> Machine -> Trip -> DepositSession -> DepositItem -> Redemption -> RewardLedger. Pengajuan pencairan memegang baris `PayoutAccount` tujuan (`FOR SHARE`) tepat setelah User agar status akun tidak berubah di tengah keputusan. Transisi pencairan (M02) mengunci User pemilik (dibaca dari `Redemption.userId` yang immutable), lalu baris Redemption, lalu baru mengubah reserve di RewardLedger.
- Setiap efek finansial baru memiliki `RewardLedger.businessKey` unik: `redemption:<id>:reserve` untuk reserve pencairan, `deposit-item:<id>:earn` untuk EARN setoran mesin, `trip:<tripId>:return` untuk reward pengembalian kantong trip, `review:<itemId>:decision:v1` untuk koreksi hasil peninjauan setoran (M04). Baris lama bernilai `NULL`.
- Backstop database: maksimal satu EARN per `depositItemId` dan satu reserve per pencairan (index unik parsial pada migration `20261013122400_wallet_keys_enforce`), serta maksimal satu reward pengembalian hidup per trip (`RewardLedger_one_earn_per_trip`: EARN dengan `reasonCode` `TRASH_BAG_RETURN` dan referensi Trip, migration `20261013151919_trip_reward_keys_enforce`; guard-nya juga menghitung reward lama yang mereferensikan ManualValidation). EARN lain yang mereferensikan trip, misalnya `TOURISM_COMPLIANCE_BONUS`, tidak termasuk. Idempotency pencairan unik per `(userId, idempotencyKey)`.
- Reward trip (M03, `lib/trip-validation.ts`): check-out massal dan scan per kantong mengunci User penerima (dibaca dari `Trip.userId` yang immutable) -> Trip -> seluruh baris `TrashBagAssignment` trip (urut id), memverifikasi ID kantong sebagai baris trip tersebut, lalu `refreshTripOutcome` menghitung ulang hasil dari semua kantong dan menulis EARN `AVAILABLE` sekali. Uang hanya dihitung dari baris kantong terverifikasi (satu baris = satu unit, `bagCount` lama tidak dikalikan); jumlah tanpa ID tidak pernah menghasilkan uang. Hanya scan yang memberi status pada kantong terakhir yang belum berstatus boleh menutup trip; scan ulang tidak pernah menutup atau membayar trip ACTIVE lama yang seluruh kantongnya sudah berstatus (dilaporkan sebagai `unclosedReviewedTrips`, ditutup hanya lewat check-out massal dengan ID). Trip yang sudah COMPLETED tidak pernah mendapat reward kedua: koreksi kondisi kantong hanya mengubah data kantong/compliance dan dicatat di audit beserta selisih reward. Migration `20261013151828_trip_reward_keys` hanya menambah index `(referenceType, referenceId)` untuk pencarian reward lama.
- Inventaris histori: `npm run reconcile:wallet` (read-only) melaporkan saldo negatif, duplikat (termasuk reward trip ganda, `duplicateTripEarn`), reserve tanpa pengajuan, baris kantong lama dengan `bagCount` selain 1 (`legacyBagUnits`, informasional: satu QR bukan otomatis beberapa unit, keputusan per trip dicatat di kasus), dan trip ACTIVE berhadiah yang seluruh kantongnya sudah berstatus tetapi belum pernah dibayar (`unclosedReviewedTrips`, dengan perkiraan reward dengan/tanpa skor aplikasi). Duplikat lama tidak pernah dihapus; prosedurnya ada di header `scripts/reconcile-wallet-history.ts`.
- Audit, notifikasi, dan transfer dijalankan setelah commit, tidak di dalam transaksi.
- Transisi pencairan (M02, `transitionRedemption` di `lib/wallet-service.ts`): status pengajuan berubah lewat compare-and-set pada status yang dibaca di bawah lock, dan reserve berubah lewat `settleRedeemLedger(redemptionId, outcome, tx)` yang hanya membuktikan settlement yang sudah sesuai atau melakukan tepat satu update bersyarat `PENDING`. Reserve hilang, jumlah/pemilik berbeda, atau outcome berlawanan menghasilkan 409 dan rollback. Mengulang outcome yang sama hanya idempotent bila ledger sudah sesuai.
- Transfer yang hasilnya tidak pasti tidak pernah ditandai gagal: pengajuan tetap PROCESSING dengan `reconciliationRequired` dan reserve tetap `PENDING` sampai hasilnya dipastikan. Idempotency key ke provider payout adalah `redemption:<id>:payout` (`payoutIdempotencyKey`), bukan `Redemption.idempotencyKey` milik klien.
- Tujuan transfer disalin terenkripsi ke `Redemption.payoutDestination*` saat pengajuan (`REQUEST_SNAPSHOT`). Pengajuan lama tanpa salinan mencatat akun saat aksi operator pertama sebagai `LEGACY_ACCOUNT_FALLBACK`, atau `LEGACY_UNAVAILABLE` bila akunnya sudah tidak ada (tidak ada nomor yang ditebak). Migration `20261013131619_redemption_destination_snapshot` hanya menambah kolom (expand), tanpa backfill. Penghapusan akun (`lib/erasure-jobs.ts`, A04) ditahan (`PENDING_RECONCILIATION`) selama pemilik masih punya saldo, pencairan berjalan, sesi setoran terbuka, atau trip aktif; setelah semuanya selesai, dalam satu transaksi di bawah lock User -> PayoutAccount -> Redemption ia mengosongkan nomor dan nama tujuan semua pengajuan pemilik (provider, sumber, dan waktu salinan tetap), menghapus catatan bebas dan tautan bukti, mengganti `providerReference` dengan sidik jari berkunci, dan antrean menampilkannya sebagai "dihapus". Ledger, `userId`, nominal, dan status tidak pernah diubah. Matriks retensi: `docs/privacy-erasure.md`.

## 5. Kebijakan reward terpusat (M04)

- Satu keputusan untuk semua jalur uang: `decideReward` (`lib/reward-policy.ts`, murni) menentukan `ACCEPTED`/`REVIEW`/`REJECTED`, jumlah, dan status ledger (`AVAILABLE` atau `PENDING`). `COMPLIANCE_ONLY` selalu 0; berat tidak valid selalu `REJECTED` tanpa uang; anomali atau material yang tidak cocok menahan 50% sebagai EARN `PENDING`. Jalur: penerimaan mesin (`lib/machine-events/acceptance.ts`), peninjauan (`lib/deposit-review.ts`), dan reward trip (`lib/trip-validation.ts`).
- Satu penulis: `creditReward` / `applyRewardEffect` (`lib/reward-credit.ts`) menulis di transaksi pemanggil setelah `lockUser`, sekali per `businessKey` (retry identik mengembalikan baris yang sama, efek berbeda dengan kunci sama = 409). Jumlah 0 tidak menulis baris. Ledger tidak pernah dipaksa: debit yang tidak lagi tertutup saldo tersedia (sudah dicairkan/ditahan untuk pencairan) dan kredit ke akun yang sudah dianonimkan (A04) ditolak menjadi `RewardReconciliationCase` berstatus `OPEN` dengan business key yang sama, tampil di laporan rekonsiliasi.
- Urutan lock reward setoran: User penerima (dari `DepositSession.userId` yang immutable) -> Machine (khusus peninjauan) -> DepositSession -> DepositItem -> RewardLedger. Transaksi event mesin hanya menyisipkan baris `MachineEvent` sebelumnya (KEY SHARE foreign key, tidak bentrok dengan lock di atas).
- Peninjauan: compare-and-set dari `REVIEW`; EARN `PENDING` dilepas (`AVAILABLE`) bila keputusan membayar, selain itu `REJECTED`; koreksi = target - semua EARN/ADJUST/REVERSE `AVAILABLE` item. Keputusan sama = idempotent, keputusan berlawanan = 409. Penahanan fraud memindahkan EARN `AVAILABLE` ke `PENDING` hanya bila saldo tersedia menutupinya, selain itu kasus `fraud:<itemId>:hold:v1`. Event mesin tidak pernah membuka ulang item `REJECTED` atau keputusan peninjau, tidak menimpa alasan item yang sedang ditinjau, dan `ITEM_REJECTED` memakai gerbang serta lock yang sama dengan penerimaan; alasan mesin berawalan `REVIEW_` diberi awalan `MACHINE_`. Item jenis tidak dikenal selalu `REVIEW` dengan reward 0; konfigurasi mesin yang tidak terbaca diperlakukan `COMPLIANCE_ONLY` + `AI_REQUIRED` (fail closed). Persetujuan hanya untuk item yang sudah melewati titik penerimaan mesin (sebelum itu hanya dapat ditolak), menolak jenis cadangan, dan memeriksa ulang berat terhadap batas tarif yang tercatat saat penerimaan (atau batas jenis bila tidak ada tarif; berat kosong tidak pernah valid) serta menghitung harga dari tarif itu; bukti harga (berat, label AI, barcode) hanya dicatat sebelum titik penerimaan, tepat saat persetujuan menjadi mungkin, sehingga tidak dapat diubah sesudahnya. `npm run reconcile:wallet` melaporkan `rejectedItemsWithMoney`: item `REJECTED` yang masih membawa uang `AVAILABLE` bersih atau `PENDING`, untuk diputuskan per kasus tanpa mengubah baris ledger. Sumbernya dua: penolakan peninjauan yang REVERSE-nya tidak lagi tertutup saldo tersedia (tetap terjadi sejak M04, sesuai desain: debit ditolak menjadi kasus `ANOMALY_ALREADY_PAID_OUT` dan EARN tetap `AVAILABLE`; kasusnya tercantum di `reconciliationCaseKeys`), serta sisa data sebelum M04 (`ITEM_REJECTED` lama yang membalik item `ACCEPTED`, atau `REVIEW_REJECTED` palsu dari mesin yang menahan saldo `PENDING`).
- Kasus rekonsiliasi `ANOMALY_ALREADY_PAID_OUT` yang terbuka menahan pencairan pengguna sebesar nominalnya (satu deposit item dihitung sekali walau punya kasus fraud dan kasus peninjauan). Keputusan peninjauan yang efek uangnya berhasil diterapkan menutup kasus item itu; kasus lain ditutup SUPERADMIN dengan catatan hasil di halaman Rekonsiliasi (`POST /api/reward-cases/[id]/resolve`, audit `REWARD_CASE_RESOLVED` tanpa teks catatan). Penutupan tidak pernah mengubah ledger.
- Item `REVIEW` tanpa catatan penerimaan yang utuh (`lib/deposit-review-contract.ts` `isLegacyReviewRow`: tanpa event penerimaan, atau dengan event penerimaan tanpa `acceptedAt`) tidak pernah dihargai dengan tarif saat persetujuan (fail closed). Peninjau hanya menyetujui item yang sudah melewati titik penerimaan. Sesi yang berakhir (`COMPLETED`/`CANCELLED`/`EXPIRED`) tidak mengakhiri sisi mesin: mesin tetap dapat melengkapi item yang belum diputuskan setelah sesi berakhir, lewat outbox-nya (bacaan, penerimaan, atau penolakan yang tertunda tetap memutuskannya, R03). Bila sesinya masih berjalan, `approve` dijawab 409 "tunggu mesin"; bila sesinya sudah berakhir, `approve` biasa dijawab 409 tanpa menyuruh menunggu, dan pesannya bergantung pada batas waktu M04 (`lib/reward-legacy-cutover.ts`: `REWARD_LEGACY_CUTOVER_AT` bila diatur, selain itu `finished_at` migrasi `20261014013000_reward_policy` di `_prisma_migrations`; tidak terbaca = tidak ada baris yang memenuhi syarat): item yang tercatat sesudah batas waktu (termasuk item `SESSION_TIMEOUT`/`SESSION_CLOSED` dari R03) hanya dapat ditolak oleh manusia; item yang tercatat sebelum batas waktu (baris lama, sebelum M04) juga dapat diselesaikan lewat persetujuan setoran lama oleh SUPERADMIN (`action: "approve", legacy: true, itemVersion: <updatedAt yang dilihat>`), yang selalu diperiksa versinya: `itemVersion` wajib (422) dan dibandingkan dengan `updatedAt` di bawah lock item (berubah = 409, tanpa tulisan). Persetujuan itu memakai gerbang, lock (User -> Machine -> DepositSession -> DepositItem), pemeriksaan berat dan business key `review:<itemId>:decision:v1` yang sama, harga dari resolusi tarif historis pada waktu tercatat item (`acceptedAt`, atau `createdAt` bila kosong; `resolveRewardRateAt`: hanya jendela tarif, `active` diabaikan, sama seperti aturan tarif tercatat, sehingga tarif yang berlaku saat itu tetap dipakai walaupun sudah dinonaktifkan dan diganti; tarif tercatat baris lama dipakai hanya bila jendelanya memuat waktu itu, dan baris lama tanpa tarif tercatat selalu ditentukan ulang pada waktu itu karena umumnya belum pernah dihargai), penanda `acceptanceEventId = legacy-approval:<superadminId>` bila belum ada event penerimaan (event asli tidak ditimpa), `acceptedAt` diisi waktu tercatat itu, dan audit `DEPOSIT_REVIEW_APPROVED` dengan `legacyApproval: true`, `pricedAt`, `sessionStatus`, `measuredWeightGrams`, `itemVersion`, `legacyCutoverAt`, `legacyCutoverSource`. Pilihan ini (bukan "tolak + kasus penyesuaian manual") diambil karena uang tertahan pengguna yang sah tidak boleh hangus hanya karena data lama, tidak ada API penyesuaian manual atau penyelesaian kasus, dan satu koreksi berkunci lebih aman daripada penulisan ledger manual. Inventaris: `reviewItemsWithoutAcceptance` (dengan `sessionEnded`, `beforeCutover`, dan `problem` `NO_ACCEPTANCE_EVENT`/`NO_ACCEPTANCE_TIME`), `acceptedItemsWithoutAcceptance` (paparan fraud: penahanan fraud memindahkannya ke jalur baris lama) dan `legacyCutover` pada `npm run reconcile:wallet`; `prisma/seed.ts` mengikuti kontrak penerimaan (event, waktu, tarif, EARN berkunci) dan diuji oleh `tests/integration/seed-contract.test.ts`.
- Tarif dipilih pada jendela UTC `[effectiveFrom, effectiveTo)` yang di-AND dengan scope campaign/organisasi/global (EX-03: dulu `OR` scope menimpa `OR` jendela sehingga tarif kedaluwarsa terpilih). Persetujuan memakai tarif yang tercatat saat penerimaan hanya bila jendelanya memuat `acceptedAt` (`rateWindowContains`, tanpa melihat `active`); tarif tercatat di luar jendelanya (sisa EX-03 pada baris lama) diabaikan dan tarif ditentukan ulang pada `acceptedAt` dengan query yang sudah diperbaiki. Baris seperti itu tercantum di `reviewItemsWithRateOutsideAcceptance`.
- Konfigurasi (migration `20261014013000_reward_policy`, expand + rekonsiliasi konfigurasi, tanpa mengubah ledger): `Machine.materialVerification` (bawaan `WEIGHT_ONLY`), `WasteType.aiAcceptedLabels` (diisi untuk PET/kaleng/Anorganik), `Organization.machineRewardMode` (bawaan `MONEY_REWARD`), `Campaign.supportsMachine` (diisi `true` untuk campaign EVENT/SCHOOL_PROGRAM yang sudah punya sesi mesin), dan tabel `RewardReconciliationCase`.
- Dana/budget reward belum dibatasi: `checkRewardFunding` adalah titik sambung B01 yang saat ini tidak memeriksa apa pun dan mengembalikan `NOT_ENFORCED_UNTIL_B01`.

## 6. Rekonsiliasi saldo global (M05)

Laporan platform `getReconciliationReport()` (`lib/reconciliation-report.ts`) dipakai `GET /api/reports/reconciliation` (SUPERADMIN), halaman `/dashboard/superadmin/reconciliation`, dan layar rekonsiliasi mobile. Modulnya terpisah dari `lib/ledger.ts` (yang memegang semantik saldo per pengguna dan penulis ledger) karena ia read model atas seluruh ledger; ia memakai ulang `computeBalance` per pengguna dan `expectedReserveStatus` per pengajuan, dan berbagi predikat ledger dengan `scripts/reconcile-wallet-history.ts` (`readUserBalances`, `findReservesWithoutRequest`). Kontrak respons berversi: `tests/fixtures/contracts/reconciliation-report.v1.json`.

- **Satu snapshot.** Semua agregat dibaca dalam satu transaksi `READ ONLY` REPEATABLE READ (`report.snapshot`), sehingga settlement yang commit di tengah laporan tidak memasangkan angka ledger sebelum settlement dengan angka pengajuan sesudahnya (selisih palsu). Laporan tidak mengambil lock baris: tidak menunggu dan tidak menahan transaksi wallet.
- **Kewajiban bersih** (rupiah bulat; `computeBalance` per pengguna lalu dijumlahkan):

  | Field | Label UI | Isi |
  | --- | --- | --- |
  | `availableLiability` | Saldo tersedia | Saldo yang dapat dicairkan, sudah dikurangi reserve dan pembayaran |
  | `pendingLiability` | Menunggu pemeriksaan | Saldo `PENDING`, belum dapat dicairkan |
  | `reservedLiability` | Sedang dicairkan | Reserve REDEEM `PENDING` milik pengajuan berjalan |
  | `paidTotal` | Sudah dibayar | REDEEM `REDEEMED`; dilaporkan terpisah, bukan kewajiban |
  | `totalObligation` | Total kewajiban | `availableLiability + reservedLiability + pendingLiability` |

  `totalOutstanding` tetap ada sebagai **alias kompatibilitas** `availableLiability` (sebelum M05 field ini berisi EARN `AVAILABLE` bruto yang tidak dikurangi pencairan); klien baru memakai `availableLiability`. `totalEarnAvailable`/`totalEarnPending` tetap berupa penerbitan bruto (informasi, bukan kewajiban).
- **Saldo minus tidak dinetting.** Saldo negatif seorang pengguna (misalnya pembayaran ganda lama) tidak mengurangi kewajiban kepada pengguna lain: kewajiban hanya menjumlahkan saldo positif, dan kekurangannya dilaporkan di `overdrawn { users, availableShortfall, pendingShortfall }` (sama dengan `negativeBalances` pada `npm run reconcile:wallet`) untuk ditangani sebagai kasus pemulihan.
- **Pencocokan pencairan per pengajuan.** Untuk setiap `Redemption`, reserve hidup milik pemilik yang sama (bukan `REJECTED`) dibandingkan dengan status pengajuan menurut `expectedReserveStatus`: `SUCCESS` dengan `REDEEMED`, `REQUESTED`/`APPROVED`/`PROCESSING` dengan `PENDING`, `FAILED`/`REVERSED` tanpa efek saldo. Baris REDEEM `PENDING`/`REDEEMED` yang tidak menopang pengajuan pemiliknya (tanpa referensi, pengajuan tidak ada, pemilik berbeda) ikut dihitung. `payoutMismatches` (maksimal 200 baris, total di `payoutMismatchCount`) mencantumkan per pengajuan: status pengajuan, status reserve, `paidDifference`, `reservedDifference`, dan `problem` (`RESERVE_MISSING`, `DUPLICATE_RESERVE`, `RESERVE_STATE_MISMATCH`, `AMOUNT_MISMATCH`, `NOT_LINKED_TO_REDEMPTION`, `MISSING_REFERENCE`, `REQUEST_NOT_FOUND`, `OWNER_MISMATCH`). Sejak M05 `redeemedDiscrepancy`/`reservedDiscrepancy` adalah jumlah **nilai mutlak** selisih per baris (sebelumnya selisih total bertanda), sehingga +100 pada satu pengajuan dan -100 pada pengajuan lain tidak menghasilkan indikator sehat palsu. `hasDiscrepancy = redeemedDiscrepancy !== 0 || reservedDiscrepancy !== 0`.
- `flaggedTransfers`: pengajuan dengan `reconciliationRequired` (M02); saldonya tetap ditahan dan termasuk `reservedLiability`. `rewardCases`: kasus M04 `OPEN`, di luar angka kewajiban sampai diselesaikan operator.
- **Organisasi sebelum B01.** Baris REDEEM tidak membawa organisasi, sehingga saldo tersedia belum dapat dibagi per organisasi tanpa mengarang atribusi. `organizations[].earnAvailable/earnPending/adjustments` adalah penerbitan bruto (informasi). `organizations[].outstanding` (saldo tersedia teralokasi) bernilai 0 dengan `allocationStatus: "UNALLOCATED_LEGACY"`, `allocationStatus` laporan `NOT_ALLOCATED_UNTIL_B01`, dan `unallocatedLegacyAmount = availableLiability - SUM(organizations[].outstanding)` (seluruh saldo tersedia). Invarian: `SUM(organizations[].outstanding) + unallocatedLegacyAmount = availableLiability`. Titik sambung B01: `readOrganizationAllocations(tx)` saat ini tidak membaca apa pun; B01/B02 (alokasi earning per sumber dan backfill histori) mengisinya. Finding LOG-07 belum CLOSED sampai itu selesai.
- `GET /api/mobile/overview` (SUPERADMIN) tetap aditif: `rewardAvailable` kini berisi `availableLiability` (sebelumnya EARN `AVAILABLE` bruto) dan field baru `rewardLiability { availableLiability, pendingLiability, reservedLiability, paidTotal, totalObligation }`. Tidak ada field yang dihapus. Dashboard web superadmin (`/dashboard/superadmin`, kartu "Reward tersedia") memakai angka yang sama (`getLiabilitySummary`), sehingga web dan mobile menampilkan saldo tersedia bersih yang sama. Angka bruto yang tersisa sengaja tidak disajikan sebagai kewajiban: "Reward diterbitkan" di laporan organisasi admin (penerbitan, bukan saldo) dan `rewardAvailable` pada `GET /api/mobile/reports` (EARN `AVAILABLE` bruto; versi per organisasi untuk ADMIN memerlukan alokasi B02, dan tidak ada layar mobile yang memakainya).
- Tidak ada migration atau backfill. Histori ledger tidak diubah; laporan hanya membaca.
- Sejak B01a laporan juga memuat `funding` (bagian 7): sisi program dari uang, dibaca dalam snapshot yang sama dan dipisahkan dari angka kewajiban pengguna di atas. Invarian `SUM(organizations[].outstanding) + unallocatedLegacyAmount = availableLiability` tidak berubah; alokasi kewajiban pengguna per organisasi tetap milik B02.

## 7. Pendanaan reward dan reservasi budget (B01a, BIZ-02)

Reward yang dijanjikan program harus tertutup kas yang sudah dikonfirmasi operator **sebelum** barang diterima. Modulnya `lib/reward-funding.ts`; migration `20261014150000_reward_funding` (expand saja: tabel dan kolom baru, tanpa menyentuh ledger).

**Model.**
- `RewardFundingAccount` (satu per organisasi, dibuat saat pertama dipakai): `confirmedRupiah` = kas yang dikonfirmasi operator dengan bukti; `heldRupiah` = kewajiban reward yang belum dibayar (batas sesi/trip yang masih direservasi + earning yang sudah dikomit). Kapasitas yang masih dapat direservasi = `confirmedRupiah - heldRupiah`. Kedua counter hanya berubah di bawah lock baris akun (`lockFundingAccount`), selalu didukung baris immutable di bawah ini, dan `version` naik setiap perubahan.
- `FundingEntry` (immutable, `businessKey` unik): entri yang **mengonfirmasi kas** (`CONFIRMED_TOPUP` dan `CORRECTION` positif) berbagi satu ruang kunci `cash:<REFERENSI>`; `CORRECTION` negatif (pembalikan) memakai `correction:<REFERENSI>`; `PAYOUT` memakai `redemption:<id>:payout:<accountId>` (negatif). Referensi dibandingkan setelah trim dan tanpa membedakan huruf besar/kecil. Tidak pernah memindahkan uang sungguhan. `reference` adalah bukti operator (minimal 6 karakter) dan satu transfer bank hanya mengonfirmasi kas sekali **lintas organisasi dan jenis**: referensi yang sama untuk organisasi, nominal, atau jenis lain ditolak 409 (`Referensi ini sudah tercatat untuk organisasi lain atau dengan nominal/jenis berbeda...`), termasuk saat dua organisasi mencatatnya bersamaan (pelanggaran index unik dipetakan ke 409 yang sama, bukan 500); referensi + organisasi + nominal + jenis yang sama idempotent 200. `note` (minimal 10 karakter: sumber dana, tanggal, rekening) wajib dan disimpan bersama entri; `verifiedById` aktornya. Kunci format lama (`topup:<orgId>:<ref>`, `topup:<ref>`) hanya pernah ada di branch yang belum dirilis ini; tidak perlu backfill.
- `RewardBudgetReservation` (`businessKey` unik): `session:<id>:admission` untuk sesi mesin, `trip:<id>:issuance` untuk kantong trip; `ceilingRupiah` maksimum kewajiban sumber itu, `remainingRupiah` yang masih dapat ditarik komit; `shortfallRupiah`/`campaignShortfallRupiah` mencatat kekurangan kapasitas yang ditemukan dalam mode bayangan; `lateReservation` menandai reservasi berbatas 0 yang dibuat pada earning pertama sumber yang diterima tanpa reservasi (program berubah menjadi berhadiah setelah penerimaan); `status` `ACTIVE`/`RELEASED` beserta siapa/kenapa dilepas.
- `RewardBudgetCommit` (`businessKey` unik = kunci earning: `deposit-item:<id>:earn`, `trip:<id>:return`): `heldRupiah` kewajiban item (batas yang dapat disetujui selama `reviewPending`), `paidRupiah` bagian yang sudah dibayar, `uncoveredRupiah` bagian yang melebihi reservasinya.
- `Campaign.rewardBudgetRupiah` (null = belum diatur; **bukan** tanpa batas), `Campaign.heldRupiah` (reservasi aktif), `Campaign.spentRupiah` (kewajiban terkomit; **tidak terisi ulang** setelah pencairan), `Campaign.maxRewardPerSessionRupiah`; `Machine.maxRewardPerSessionRupiah`, `Machine.maxItemsPerSession` (cadangan bila program tidak menetapkan; `maxItems` diikat ke lease oleh B01b). Semua nullable saat expand. Nilai cap yang dikonfigurasi minimal Rp1 (API menolak 0; nol atau negatif dianggap belum diatur, `configuredCap`). Ketika penegakan aktif, program `MONEY_REWARD` berstatus `ACTIVE` wajib memiliki kuota >= Rp1 (422 `Kuota reward program wajib diisi sebelum program berhadiah diaktifkan`) dan, bila berjalan di mesin, batas per sesi >= Rp1 (422 `Batas reward per sesi wajib diisi sebelum program berhadiah diaktifkan`); program tanpa kuota tidak menerima setoran (409 `Kuota reward program belum diatur...`). Dalam mode bayangan program seperti itu dilaporkan (`programsWithoutBudget`).

**Siklus.**
1. *Admisi* (`reserveRewardBudget`): scan mesin mereservasi batas per sesi (program, lalu mesin) untuk sesi `MONEY_REWARD`; penerbitan kantong mereservasi `kantong x Rp2.000 x multiplier` (`tripIssuanceCeiling`, diperluas setiap penerbitan). Pemeriksaan persis seperti brief: `confirmed - held < ceiling` -> 409 `Program sementara tidak menerima setoran berhadiah`; `budget - held - spent < ceiling` -> 409 `Kuota reward program tidak mencukupi`. Penolakan terjadi sebelum sesi/kantong dibuat (rollback transaksi yang sama); reservasi berbatas 0 juga ditolak saat penegakan aktif (batas 0 bukan admisi). `COMPLIANCE_ONLY` tidak mereservasi apa pun dan tidak membuat entri dana. Idempotent per `businessKey`. Trip yang dibatalkan melepas reservasinya; **membuka ulang** trip (CANCELLED -> PLANNED, `changeTripStatus` di `lib/trip-issuance.ts`, di bawah lock trip yang sama) mereservasi ulang seluruh kantong yang sudah diterbitkan di atas yang masih terkomit (409 saat penegakan aktif bila kapasitas tidak menutup; trip tetap CANCELLED).
2. *Penerimaan* (`checkRewardFunding` di `lib/reward-credit.ts` -> `commitRewardAgainstBudget`): setiap EARN mengubah hold admisi menjadi hold kewajiban tanpa mengurangi kas (`remainingRupiah` turun, `heldRupiah` akun tetap; campaign `held` turun dan `spent` naik). Dikunci dengan kunci earning, sehingga event retry/duplicate `localEventId` tidak memakai dana dua kali. Item yang ditahan untuk ditinjau mengomit **batas yang dapat disetujui** (base pada tarif admisi) dengan `reviewPending`. Komit tidak pernah ditolak: barang yang sudah diterima tidak kehilangan reward; kelebihan di atas reservasi dicatat `uncoveredRupiah` (akun `held` naik) dan tampil di laporan. Batas admisi membatasi event offline/terlambat; item tidak dihargai ulang dengan konfigurasi baru. Sumber **tanpa reservasi** (`resolveSourceReservation`, dipakai oleh penerimaan, penyelesaian trip, dan keputusan peninjauan): bila dibuat sebelum batas waktu pendanaan ia kewajiban legacy yang di-backfill B02 (tidak dikomit); bila sesudahnya (program berubah menjadi berhadiah setelah penerimaan) reservasi berbatas 0 dibuat saat itu (`lateReservation`) dan seluruh earning dikomit `uncovered`, sehingga tetap terhitung di `heldRupiah` dan laporan (`ADMITTED_WITHOUT_RESERVATION`). Batas waktu pendanaan = yang **lebih awal** antara `REWARD_FUNDING_CUTOVER_AT` (bila diatur) dan `finished_at` migrasi `20261014150000_reward_funding`, sehingga pengaturan yang lebih lambat dari migrasi tidak pernah memperluas jendela legacy; nilai tak terbaca = fail closed (semua sumber dianggap sesudahnya); batas waktu M04 (`REWARD_LEGACY_CUTOVER_AT`) tidak berubah. Saat penegakan aktif, program yang masih memiliki sesi terbuka atau trip PLANNED/ACTIVE berkantong tidak dapat **mulai membayar uang** atau menaikkan multiplier (409 `Program masih memiliki sesi setoran atau trip yang berjalan...`, `guardProgramRewardChange` di bawah lock Campaign). "Mulai membayar" dinilai dari mode **efektif** (`tripRewardMode`/`machineRewardMode`, yakni `rewardMode` bersama `campaignType` dan `supportsMachine`), sehingga mengubah tipe program (misalnya TRASH_BAG -> EVENT lalu kembali ke TRASH_BAG setelah kantong diterbitkan tanpa reservasi) atau `supportsMachine` yang membuat trip/mesin mulai membayar juga ditolak selama sumbernya terbuka. Mode mesin organisasi tidak dapat berubah ke uang selama ada sesi tanpa program yang terbuka (409, `guardOrganizationModeChange` di bawah lock akun); mode bayangan mengizinkannya dan menanganinya lewat reservasi terlambat di atas.
3. *Peninjauan* (`settleOrCommitReward`): keputusan menetapkan kewajiban ke target (approve) atau 0 (reject) dan melepaskan selisihnya ke kapasitas organisasi dan kuota program; koreksi yang ditolak menjadi kasus rekonsiliasi mempertahankan kewajiban. Keputusan mengunci akun pendanaan **reservasi sesi** (dibaca dari reservasi yang immutable sebelum lock, lalu Campaign -> Machine -> DepositSession -> DepositItem), bukan akun organisasi mesin saat ini; sesi tanpa reservasi mengunci akun organisasi mesinnya. Di bawah lock, organisasi mesin dibaca ulang dan harus pemilik akun itu: mesin yang sudah dipindah ke organisasi lain ditolak 409 tanpa keputusan dan tanpa efek dana. Penahanan fraud menandai komit `reviewPending` lagi (di bawah lock User pemilik) sehingga pencairan tidak menariknya.
4. *Pencairan sukses* (`settlePayoutFunding`, di dalam transaksi `transitionRedemption` M02; lock User -> setiap akun pendanaan sumber (urut id) -> Redemption): gross dialokasikan ke komit pengguna yang sudah dapat dibelanjakan, **komit tertua lebih dulu** (aturan sementara B01a; alokasi per lot B02 menggantikannya di satu tempat ini), satu `FundingEntry PAYOUT` per akun sumber, `confirmedRupiah` dan `heldRupiah` turun sebesar yang dialokasikan, `paidRupiah` komit naik. Gross di luar kewajiban terdanai adalah saldo legacy (sebelum B01a) dan tetap di bucket `unallocatedLegacyAmount` M05 sampai backfill B02: tidak ada sumber yang dikarang. Urutan alokasi tidak mengubah kapasitas (`confirmed - held` berkurang nol). Pembatalan/kegagalan pencairan mengembalikan saldo pengguna tetapi **tetap kewajiban dana**: tidak ada entri dan `held` tidak berubah. Kuota campaign yang sudah dikonsumsi tidak terisi ulang.
5. *Sisa reservasi*: reservasi trip ditutup saat trip COMPLETED (setelah komit reward kembali) atau CANCELLED. Sisa reservasi **sesi** dipertahankan sampai **close watermark** dari mesin (B01b: event `SESSION_CLOSE_WATERMARK` yang dikirim RVM hanya setelah server mengakhiri sesi dan semua event sesi ter-ACK; `lib/machine-events/watermark.ts` mengunci akun reservasi (bukan organisasi mesin saat ini; mesin yang pindah organisasi ditolak 409), memverifikasi jumlah event, mencatat `DepositSession.closeWatermarkAt`, lalu melepas `sisa - eksposur` dengan kunci `session:<id>:close-watermark` pada tabel `RewardBudgetRelease` (retry tidak melepas dua kali); **eksposur** = untuk setiap item yang sudah melewati titik penerimaan tetapi masih menunggu peninjau, batas item terbesar snapshot dikurangi yang sudah dikomit untuk item itu (`sessionReviewExposure`), tetap ditahan dan reservasi tetap ACTIVE; keputusan peninjauan yang menyisakan tidak satu pun item seperti itu menutup sisanya dengan kunci `session:<id>:review-close` (`closeWatermarkedSessionIfSettled`); audit `DEPOSIT_SESSION_CLOSE_WATERMARK`) atau dilepas secara eksplisit oleh SUPERADMIN (`POST /api/organizations/{id}/funding {action:"release_reservation", reservationId, reason}`, hanya untuk sesi/trip yang sudah berakhir, audit `REWARD_RESERVATION_RELEASE`); tidak pernah oleh timeout. Koneksi mesin yang hilang berarti tidak ada watermark: sisa tetap ditahan (`SOURCE_CLOSED_AWAITING_WATERMARK`). Penerimaan terlambat setelah pelepasan tetap membayar dan dicatat `uncovered`. Untuk guard perubahan program (butir 2), sesi yang sudah berakhir tetap dianggap **terbuka** selama belum ada watermark dan masih punya item belum diputuskan (PENDING/REVIEW), selama sesudah watermark masih punya item yang sudah melewati titik penerimaan tetapi belum diputuskan, atau selama reservasinya masih ACTIVE (`openSessionWhere`, `countHeldEndedSessions`); sesi dengan semua item diputuskan dan reservasi dilepas dianggap tertutup. Setiap pelepasan parsial wajib berkunci (`releaseUnusedRewardBudget` menolak `close:false` tanpa `businessKey`).

**Flag `REWARD_FUNDING_ENFORCED`** (env server, bukan `NEXT_PUBLIC_`; hanya nilai persis `true` yang menegakkan; nilai lain selain `false`/kosong dianggap salah bentuk dan fail closed ke tidak menegakkan dengan peringatan). Tanpa flag = **mode bayangan**: seluruh reservasi, komit, pelepasan dan entri pencairan dicatat persis seperti mode tegak, pemeriksaan kapasitas dihitung dan kekurangannya disimpan pada reservasi (`shortfallRupiah`, `campaignShortfallRupiah`) serta dilaporkan, tetapi tidak ada admisi/penerbitan/aktivasi program yang ditolak; sesi tanpa batas per sesi diterima dengan batas 0 dan dilaporkan `CEILING_NOT_CONFIGURED`. Urutan rollout: (1) deploy expand ini dalam mode bayangan; (2) operator mencatat dana terkonfirmasi dengan bukti (`POST /api/organizations/{id}/funding`, SUPERADMIN, idempotent per referensi: referensi sama + nominal sama = 200 tanpa entri baru, nominal berbeda = 409) dan mengisi `maxRewardPerSessionRupiah`/`rewardBudgetRupiah`; (3) B02 backfill kewajiban pembuka dari histori ledger ke `heldRupiah` dan menyelesaikan funding gap (tidak diisi dengan topup palsu); (4) baru `REWARD_FUNDING_ENFORCED=true`. Flag true tidak berarti BIZ-02 ditutup; rilis uang tetap di gate Z01.

**Lock.** Urutan global tetap User -> PayoutAccount -> RewardFundingAccount -> Campaign -> Machine -> Trip -> DepositSession -> DepositItem -> Redemption -> RewardLedger: scan (User -> akun -> Campaign -> Machine), penerimaan dan peninjauan (User -> akun -> Campaign -> [Machine ->] DepositSession -> DepositItem), penerbitan kantong dan hasil trip (`lockTripAggregate`: User -> akun -> Campaign -> Trip -> kantong), pencairan sukses (User -> akun-akun sumber -> Redemption), topup/koreksi/pelepasan sisa (akun saja). Fungsi `lib/reward-funding.ts` mengambil ulang lock akun/campaign secara re-entrant; pemanggil mengambilnya lebih dulu pada urutan di atas.

**Pemantauan.** `report.funding` (`GET /api/reports/reconciliation`, halaman rekonsiliasi superadmin) dan `GET /api/organizations/{id}/funding` (SUPERADMIN, atau ADMIN organisasinya) menampilkan per organisasi: dana terkonfirmasi, kewajiban ditahan, kapasitas, reservasi aktif beserta sisanya, kewajiban di luar reservasi, program berhadiah aktif tanpa kuota (`programsWithoutBudget`), dan reservasi yang perlu ditangani beserta pemilik (`userId`, organisasi, sumber) dan alasan rekonsiliasinya: `SOURCE_CLOSED_AWAITING_WATERMARK` (sumber berakhir, sisa masih ditahan), `SOURCE_OPEN_TOO_LONG` (> 24 jam), `CEILING_NOT_CONFIGURED`, `CAPACITY_SHORTFALL` (mode bayangan), `ADMITTED_WITHOUT_RESERVATION` (sumber diterima tanpa reservasi, lihat butir 2).
